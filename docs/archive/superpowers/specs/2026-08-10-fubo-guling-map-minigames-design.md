# 伏波古岭中型地图与独立小游戏设计

> Status: superseded on 2026-08-10. The four-plate and modular-environment direction in this historical draft must not be implemented. Current canonical truth is in `docs/design/fubo-guling-slice.md`, `docs/design/art-direction.md`, and `docs/changes/CHG-20260810-fubo-guling-medium-map-minigames.md`.

- Historical status: previously approved, now superseded
- Date: 2026-08-10
- Engine: Godot 4.7.1
- Target: desktop and Web export

## 1. Goal

将伏波古岭制作成一张具有相机跟随和“移步换景”体验的中型岭南岛屿地图。玩家先在地图上探索，到达特定地点并完成简短剧情确认后，进入独立全屏轻量小游戏；小游戏不要求继续操控地图角色，完成后返回原地图并推进任务。

场景只包含两项小游戏：鼠标操作的“三渠引水”和键盘操作的“听令回鼓”。每项正常游玩时长为 1–2 分钟，失败只重置当前小回合。

## 2. Non-goals

- 不制作完整开放世界、战斗、经济、室内探索或第三项小游戏。
- 不为背景中的每棵树、每块石头和每件装饰建立独立节点或碰撞。
- 不创建操作系统级独立窗口；“独立全屏”指 Godot 内部的全屏 `PackedScene`。
- 不从生成图片的颜色或 Alpha 自动推导碰撞。
- 不让单张生成图同时展示五个地点或完整岛屿轮廓。
- 不要求音游级严格节拍判定。

## 3. Player flow

```text
码头进入伏波古岭
  → 探索并找到守岭人
  → 守岭人简短剧情，开放古渠任务
  → 玩家步行到古渠入口
  → 古渠现场提示与“开始挑战 / 稍后再来”
  → 全屏“三渠引水”
  → 返回地图，开放前往校场的道路
  → 到达校场并播放简短剧情
  → 全屏“听令回鼓”
  → 返回地图，开放观景台
  → 到达观景台，完成切片
```

进入小游戏前必须由玩家在对应地点确认。选择“稍后再来”时保持地图状态，玩家可再次接近入口触发。守岭人对话只开放古渠任务，不在守备院直接启动小游戏。完成小游戏后角色回到入口附近的安全落点，而不是触发区中心，以防立即重复触发。

## 4. Map scale and camera

- 世界有效范围定为约 `3200×2200`，不再沿用当前 `2600×1500` 的紧凑尺度。
- 设计视口为 `1344×896`；正常跟随相机一次只能看见当前地点和部分相邻道路。
- 地图约为 2.4 个横向镜头、2.5 个纵向镜头，能形成明显的区域过渡，但不会产生长时间纯走路。
- 推荐地点锚点：码头 `(420, 1850)`、守备院 `(1150, 1650)`、古渠 `(2600, 1180)`、校场 `(1850, 620)`、观景台 `(2550, 320)`。
- 主道路净宽保持 `160–240` 世界像素，至少允许两名 64×64 角色并行。
- 摄像机限制在世界边界，保持平滑跟随；任何正常镜头都不能同时看清五个地点。

## 5. Visual direction

目标是清新明朗的中式像素风，而不是厚重写实像素风：

- 低至中等对比、短而柔和的日间阴影、清晰像素簇和较大的纯净色块。
- 浅灰砖、青灰瓦、淡米黄夯土路、清亮青蓝海水和鲜嫩草木绿。
- 岭南身份来自灰砖镬耳墙、青灰硬山瓦顶、花岗岩古渠、榕树、荔枝、竹丛、海防台和中国军镇陈设。
- 禁止暗色旧化、密集噪点、写实材质、戏剧性光照、完整微缩岛屿、日本神社、东南亚寺庙、欧式城堡和热带度假村语言。

现有一次性完整岛屿生图只作为配色和布局参考，不作为正式地图底图。

## 6. Image-generation-aware map pipeline

生图模型容易把提示词中的全部地点压缩进同一画面，也难以稳定输出可无缝拼接的 TileSet。因此采用“统一风格的连续局部底图 + 少量独立物件”，不采用完整岛屿单图或全生成 TileSet。

### 6.1 Four local background plates

- 先在 Godot 灰盒中锁定世界边界、五个锚点、道路、院落、触发区和不可进入区域。
- 正式背景由 4 张连续局部图组成：西南码头/守备院、东南山腰过渡、西北校场山路、东北古渠/观景台。
- 每张图只描绘一个或两个相邻地点，不能知道或展示全岛全貌。
- 相邻图保留 12–15% 的低细节重叠区；接缝放在草地、缓坡或宽道路上，不放在建筑、入口、悬崖尖角或高对比浪花上。
- 下一张局部图以上一张的边缘裁片为参考进行延展，锁定相同俯视角、色板、像素密度和光照方向。
- 模型输出若小于目标板块尺寸，只允许最近邻等比放大且不超过 1.25 倍；多余边缘通过裁切处理，不做非等比拉伸。

### 6.2 Baked and independent content

烘焙进局部底图：

- 草地、泥路、普通石阶与铺地。
- 远离道路的树林、竹丛、散石和花草。
- 悬崖、海岸、不可进入的山坡。
- 不可进入的远景建筑群、院墙和普通地基。

保留为 Godot 独立节点：

- 守岭 NPC、玩家和剧情相关角色。
- 紧贴道路且必须遮挡角色的少量房屋、屋顶和树冠。
- 古渠闸门、动态水流、小游戏入口、军鼓、旗帜和剧情障碍。
- 预计只保留 10–15 个关键独立视觉对象。

比例以 64×64 玩家为基准：主要近景建筑宽 `256–320`，普通独立树冠宽 `96–128`，交互机关宽 `64–96`。所有导入纹理使用最近邻过滤。

## 7. Collision and occlusion

- 可游玩空间由宽道路、院落、古渠操作入口和校场入口组成。
- 密林、山体、海岸、远景建筑群等非游玩区域由约 6–10 个大型 `CollisionPolygon2D` 或矩形碰撞整体封闭。
- 道路转角只补少量碰撞形状，不为底图中的单件装饰建立碰撞。
- 玩家可接近的房屋只在墙基设置碰撞；屋顶和树冠不参与碰撞，通过 Y 排序或独立遮挡层覆盖角色。
- 被大块碰撞封闭的背景装饰无需分层，因为玩家不能走到其后方。
- 触发区和大型禁行区继续由 Godot 手工维护，不与生成图片自动绑定。

## 8. Minigame technical architecture

使用 Godot 原生 GDScript 和独立 `PackedScene`，不引入第三方框架。

```text
FuboGuling
├─ World                     地图、角色、碰撞与触发
├─ HUD
└─ MinigameHost              全屏小游戏宿主
   └─ ActiveMinigame         运行时实例化的独立 PackedScene
```

### 8.1 Components

- `FuboMinigameHost`：负责实例化、淡入淡出、输入隔离、防止重复创建和恢复地图。
- `FuboMinigameBase`：定义统一的 `completed(result)`、`exit_requested` 和 `round_restarted` 接口。
- `FuboCanalMinigame`：独立全屏 `Control` 场景，接收鼠标输入。
- `FuboDrumMinigame`：独立全屏 `Control` 场景，接收键盘输入。
- `FuboGuling`：只决定触发时机和完成后的任务门控，不处理小游戏内部操作。

小游戏打开时地图节点暂停并隐藏，角色输入关闭且移动目标清空；宿主和小游戏设为暂停时仍处理。完成或主动离开后销毁小游戏并恢复原地图实例，因此角色位置、相机和世界状态无需序列化或重新加载。

## 9. Minigame one: 三渠引水

- 独立画面上方为来水口，下方为左、中、右三块蓄水田。
- 每轮显示目标水量，并提供与目标总量相等的若干股水。
- 玩家点击木闸切换分流方向，再点击“放水”释放一股水。
- 水流沿石渠播放可见动画，进入目标田后水位增加；达到目标的田块亮起。
- 超过目标或进入封闭支渠时只重置当前轮，并保留同一目标重新开始。
- 三轮分别分配 3、4、5 股水；后两轮随机改变目标分配，并随机封闭一条不影响可解性的支渠。
- 出题器在生成题目后用同一逻辑验证至少存在一条解法；无解题目不进入表现层。
- 不设倒计时。预计完成时间 60–90 秒。
- 根据总操作次数给出“善治、通达、疏浚”评价，评价不影响剧情推进。

## 10. Minigame two: 听令回鼓

- 独立校场画面显示左、中、右三面军鼓。
- `A/S/D` 分别控制左、中、右鼓；方向键左/下/右提供兼容映射。
- 每轮先自动演示鼓令，鼓面闪动并播放对应鼓声；演示期间不接收玩家提交。
- 演示后节拍线移动，玩家按记忆在宽松判定区内回敲。
- 判定分为正拍、稍迟和失误；正拍与稍迟都算通过，不要求专业音游精度。
- 三轮长度为 4、5、6 拍。每次游戏随机生成序列、速度和小幅节拍间隔变化。
- 每轮基础速度从 `72/84/96 BPM` 中随机选择，且不得与上一轮相同；单拍间隔只允许在基础间隔上做 `±8%` 变化。
- 输入距离目标拍点 `±120 ms` 显示“正拍”，`±121–280 ms` 显示“稍迟”并继续，超过 `±280 ms` 或按错鼓判定为失误。
- 相邻鼓不连续重复；第三轮保证三面鼓都出现。
- 失误只重置当前轮，答案保持不变并自动重播。
- 预计完成时间 60–90 秒。

## 11. Drum audio

正式玩法必须使用三份可明显区分的鼓类音频素材，不使用当前正弦提示音，也不只依靠同一素材的轻微移调：

- 左鼓：低沉厚实的鼓心重击，长尾音。
- 中鼓：中频紧实的普通鼓击，短尾音。
- 右鼓：清脆的鼓边击，明显木质瞬态。

三种声音同时使用不同鼓面颜色、敲击动画和轻微左右声像辅助识别。演示和玩家输入使用完全相同的三种映射。失败提示使用单独的低沉收鼓声，不能与答案声音混淆。

## 12. Entry, exit, pause and focus handling

- 守岭人对话完成后只解锁古渠入口；首次进入古渠或校场的对应触发区时播放简短现场提示，然后显示“开始挑战 / 稍后再来”。
- 转场期间锁定确认输入，避免连续按键创建多个小游戏实例。
- `Esc` 打开“继续挑战 / 暂时离开”确认。暂时离开会重置本次小游戏进度并返回地图，但不标记任务完成。
- 完成后宿主发出结果，地图推进任务阶段、关闭对应触发并开放下一段道路。
- 网页版失去焦点时自动暂停节奏、计时和输入；恢复焦点后显示三拍倒数再继续当前演示或输入阶段。
- 小游戏打开时地图移动、互动和调试输入不能穿透；返回地图后输入状态必须完整恢复。

## 13. State and result contracts

小游戏完成结果使用小型字典传回地图：

```gdscript
{
    "game_id": "canal" or "drum",
    "completed": true,
    "rating": String,
    "mistakes": int,
    "duration_ms": int,
}
```

地图只依赖 `game_id` 和 `completed` 推进流程；评价、失误数和耗时用于结果显示与测试，不影响主线解锁。

## 14. Verification

### Automated

- 宿主同一时间只能创建一个小游戏，完成和退出均恢复地图处理与角色输入。
- 水渠三轮随机题目全部有解，错误只重置当前轮，完成结果字段完整。
- 军鼓随机序列符合长度、无相邻重复和第三轮包含三鼓的约束。
- 军鼓输入在宽松时间窗内通过，错误只重置当前轮；失焦时不推进计时。
- 返回地图后任务阶段、角色位置、相机限制和道路门控保持正确。

### Manual playtest

- 在 `1344×896`、常见宽屏和 Web 画布上完整显示两个小游戏。
- 两项小游戏首次游玩均能在 1–2 分钟理解并完成。
- 三种鼓声音色在普通扬声器和低音量下仍可明显区分。
- 正常地图镜头不能同时看清五个地点，沿路线移动时能依次出现新景观。
- 玩家不能进入大块封闭背景区，也不会在道路边缘被零碎碰撞频繁卡住。
- 至少一座近景房屋和一棵近景树正确表现人物前后遮挡。
- Godot 运行日志无解析错误、重复触发错误或场景恢复错误。

## 15. Acceptance summary

设计完成的判定是：伏波古岭成为一张中型、清新中式、相机跟随的连续探索地图；玩家通过地点触发进入两个操作方式不同的独立全屏小游戏；地图不需要逐件精细建模，生图模型只负责连续局部底图和少量关键素材；碰撞、遮挡、任务状态和小游戏输入均由 Godot 结构化维护。
