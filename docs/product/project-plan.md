# 《厂车英雄传》项目计划书

- Status: draft-for-review
- Version: 0.1
- Owner: TSOC
- Last updated: 2026-07-21
- Target engine: Godot .NET 4.7.1
- Target platform: Windows / Steam

## 1. 执行摘要

《厂车英雄传》计划从当前“皇宫受命 → 南疆水师”的连续剧情原型，发展为一款以岭南海防为题材的俯视角混合 2.5D 单机 RPG。玩家扮演奉旨南下的水师主帅，在海疆舆图上探索港口与岛屿，招募将领、训练水师、筹措舰船并指挥小规模实时战斗，最终改变地方官府、商帮、海民与海盗之间的力量格局。

目标画面路线为：

> 2D 手绘背景 + 低模 3D 人物 + 固定正交 3D 镜头 + 卡通渲染 + 2D UI/立绘。

当前项目仍是纯 2D 原型：场景一使用 GDScript，场景二使用 C#，角色为 `CharacterBody2D + AnimatedSprite2D`。本计划不把目标架构描述为已经完成，也不要求立刻重写现有两幕。第一优先级是在独立验证场景中证明混合 2.5D 管线、同屏单位性能和基础小队战斗成立；验证通过后，才进入批量资产生产和正式场景迁移。

## 2. 产品定位

### 2.1 一句话介绍

玩家奉旨出任岭南水师主帅，在动态变化的海疆中招将练兵、筹船筑防、清剿海盗、收复岛屿，并通过军事与政治选择决定沿海秩序。

### 2.2 类型与规模

- 类型：俯视角混合 2.5D、半开放世界、实时小队战斗、轻经营、剧情沙盒 RPG。
- 模式：单人离线。
- 首发平台：Windows / Steam。
- 目标玩家：喜欢中国历史幻想、角色养成、小队战斗、势力关系和地图探索的玩家。
- 世界观：暂按架空明代岭南、低魔或无魔设计；正式世界观另行评审。
- 首个公开目标：1.5～2 小时 Steam Demo。
- 正式版远期目标：12～20 小时主线与支线内容；该数字不是本阶段承诺。

### 2.3 玩家承诺

1. 玩家能感受到“奉旨整顿海疆、从无到有建立水师”的身份成长。
2. 战斗乐趣来自直接操控主帅与下达军令，而不是只看自动战斗。
3. 港口、人物和敌对势力会对玩家的选择产生可见变化。
4. 岭南海防、舰队建设与海岛争夺构成区别于常见陆战沙盒的主题识别度。

## 3. 技术路线决策

### 3.1 评估过的路线

| 路线 | 核心思路 | 适用场景 | 优点 | 缺点 | 学习成本与未来价值 |
|---|---|---|---|---|---|
| A. 纯 2D 像素/手绘 | 背景和角色全部使用 2D 帧动画 | 快速完成短篇剧情 RPG | 最大限度复用当前原型，开发成本最低 | 大量方向和动作会造成帧数膨胀，部队换装与转身成本高 | 学习成本低；适合短篇，长期扩军价值有限 |
| B. 2D 运行时伪 2.5D | 纯 2D 角色配合 Y 排序、前景遮挡、阴影和分层地图 | 不具备 3D 美术能力的小团队 | 仍可保留完整 2D 工作流，视觉纵深优于普通平面场景 | 角色仍需逐方向动画，无法充分解决大规模兵种复用 | 学习成本中等；适合作为失败回退方案 |
| C. 混合 2.5D | 2D 背景、低模 3D 角色、固定正交镜头、卡通渲染 | 需要大量士兵、装备变体和动作复用的长期项目 | 骨骼和动作可复用，转身自然，适合小队战斗和兵种扩展 | 需要新建 3D 模型、绑定、渲染、导航和镜头匹配管线 | 学习成本高；一旦管线稳定，长期生产价值最高 |

### 3.2 已选路线

选择路线 C，但采用“先验证、后迁移”的执行方式。

选择理由：

- 水师、海盗和多兵种会产生大量共用动作，3D 骨骼比逐帧绘制更易复用。
- 头盔、服装、武器和配色可以通过模块化网格快速形成单位变体。
- 固定镜头能够压缩模型精度需求，并通过卡通渲染接近 2D 手绘观感。
- 当前纯 2D 原型仍能承担剧情、文案、交互和流程验证，不必立即推倒重来。

### 3.3 明确不采用的做法

- 不做自由旋转镜头。
- 不做写实 PBR 角色和复杂实时光照。
- 不把皇宫与甲板完整建成写实 3D 场景。
- 不在技术验证前批量制作正式角色。
- 不用 `SubViewport` 为每名角色单独渲染 3D 立绘；这会增加同步和性能负担。
- 不以预渲染序列帧作为首选，但保留为验证失败后的回退方案。

## 4. 目标 Godot 技术架构

### 4.1 当前原型与目标生产架构

| 项目 | 当前原型 | 目标生产架构 |
|---|---|---|
| 世界根节点 | `Node2D` | 本地探索/战斗使用 `Node3D`；海疆舆图可保留 `Node2D` |
| 角色 | `CharacterBody2D` + `AnimatedSprite2D` | `CharacterBody3D` + `Skeleton3D` + `AnimationTree` |
| 镜头 | `Camera2D` | 固定角度、正交投影 `Camera3D` |
| 背景 | 单张 `Sprite2D` | 与镜头投影匹配的纹理平面/分层 `MeshInstance3D` 或 `Sprite3D` |
| 碰撞 | `CollisionPolygon2D` | `StaticBody3D` + 简化 `CollisionShape3D` |
| 寻路 | 直线移动与手工限制 | `NavigationRegion3D` + `NavigationAgent3D` + 编队锚点 |
| 阴影 | 背景自带或无 | 统一脚底投影贴片；必要时使用受控实时阴影 |
| UI | `CanvasLayer` + `Control` | 继续使用 `CanvasLayer` + `Control`，不迁移到 3D UI |
| 数据 | 场景脚本内硬编码 | 自定义 `Resource` 数据 + 版本化存档 |

### 4.2 场景渲染结构

本地探索与战斗场景以 `Node3D` 为根，采用固定正交镜头。背景不是简单铺在屏幕后方，而是由与镜头投影匹配的若干纹理平面组成：地面/后景、角色活动层、前景遮挡层。美术必须在锁定镜头后按同一投影制作，避免每张地图单独手调角色脚点。

建议的渲染顺序：

```text
2D 后景/天空
→ 纹理地面与建筑后层
→ 3D 角色、武器、可交互物
→ 屋檐、船帆、树冠等前景遮挡层
→ 2D 特效补充层
→ CanvasLayer UI、立绘与字幕
```

所有单位站立在统一的 XZ 地面平面上，Y 轴只表达真实高度或短暂跳起，不参与传统 2D 的脚底排序。角色移动由代码控制，动画默认不使用 Root Motion，避免编队单位发生累计位移误差。

### 4.3 Godot 运行时组件

| 领域 | Godot 组件/方案 | 用途 |
|---|---|---|
| 场景 | `Node3D`、`PackedScene` | 本地探索、甲板、海滩、岛寨和战场 |
| 摄像机 | `Camera3D`，Orthogonal | 锁定投影、角度、缩放和构图 |
| 单位 | `CharacterBody3D`、`CollisionShape3D` | 主帅、英雄、士兵与敌人 |
| 骨骼动画 | `Skeleton3D`、`AnimationPlayer`、`AnimationTree` | 动作复用、状态混合与攻击窗口 |
| 寻路 | `NavigationRegion3D`、`NavigationAgent3D` | 路径请求、局部避让和战场移动 |
| 编队 | 自定义编队锚点与槽位 | 跟随、坚守、集结、齐射和冲锋 |
| 背景 | `MeshInstance3D`/`Sprite3D` + 纹理 | 2D 手绘地面、建筑和遮挡层 |
| 材质 | `ShaderMaterial` | 色阶卡通渲染、描边、受击闪白和阵营染色 |
| 影子 | `Decal` 或贴地 `QuadMesh` | 统一脚底软阴影，降低对实时灯光依赖 |
| 特效 | `GPUParticles3D`、`AnimatedTexture` | 烟尘、炮火、水花、箭矢和命中特效 |
| UI | `CanvasLayer`、`Control`、`Theme`、`NinePatchRect` | 对话、军令、队伍、地图、任务和设置 |
| 音频 | `AudioStreamPlayer`、`AudioStreamPlayer3D` | UI、环境、战斗和空间音效 |
| 数据 | C# 自定义 `Resource` | 英雄、兵种、舰船、技能、阵营和任务定义 |
| 存档 | `FileAccess` + 版本字段 | 世界状态、队伍、任务与设置持久化 |

### 4.4 语言与代码边界

- 当前混合 GDScript/C# 原型保持可运行，不做无收益重写。
- 新增长期系统优先使用 C#：战斗、单位、编队、世界状态、数据模型和存档。
- GDScript 暂时保留在场景一剧情原型；当迁移收益大于风险时再单独立项转换。
- UI 场景可以继续由编辑器搭建，行为脚本遵循所属模块的主语言。
- 核心数值和状态不得继续硬编码在单个场景脚本中。

### 4.5 数据模型

计划建立以下数据资源，名称表示职责，不代表当前已经实现：

- `HeroData`：英雄身份、属性、专长、立绘和关系标签。
- `TroopData`：兵种、成长、装备槽、单位场景和升级路线。
- `ShipData`：舰船类型、载员、耐久、航速与武器槽。
- `SkillData`：技能条件、冷却、目标规则和效果描述。
- `FactionData`：阵营、关系、资源与行为倾向。
- `SettlementData`：港口/岛寨归属、服务、产出和事件表。
- `QuestData`：任务阶段、条件、奖励与世界状态修改。
- `WorldState`：时间、地点归属、威胁、事件和玩家进度。

内容数据与运行时状态分离。资源文件只描述静态定义，存档只保存变化值和稳定 ID，避免场景路径改变后旧存档全部失效。

### 4.6 工具与资产管线

- Godot .NET 4.7.1：运行时、场景和资源导入。
- .NET SDK 9：C# 编译与纯逻辑测试。
- Blender：低模、绑定、权重和动作检查；如需安装或升级，一律安装到 `D:/Programs/`。
- 推荐交换格式：源文件 `.blend`，Godot 导入文件 `.glb`。
- 2D 源文件：分层 PSD/KRA/Aseprite 等；运行时导出 PNG 或经质量验证的 WebP。
- Git：代码与文档版本管理。
- Git LFS：进入批量生产前评估用于 `.blend`、`.glb`、大尺寸分层源图和无损音频；未验证仓库配置前不直接启用。
- 自动验证：Godot `--headless`、现有 PowerShell 验证脚本，以及后续为纯 C# 规则层增加的单元测试。

## 5. 核心玩法计划

### 5.1 核心循环

```text
接受军令
→ 海疆航行与探索
→ 进港交涉、贸易或招募
→ 遭遇海盗、岛寨或护航任务
→ 实时小队战斗
→ 获取资源、声望与人物关系变化
→ 扩军、造船、升级技能
→ 改变地区局势并推进主线
```

短循环目标为 10～15 分钟，章节循环目标为 60～90 分钟。

### 5.2 四类游戏场景

1. 海疆舆图：舰队移动、港口与岛屿、敌军、时间、天气和随机事件。
2. 城镇/剧情场景：皇宫、广州港、水师营地、船坞与人物交互。
3. 实时战场：甲板战、海滩登陆、岛寨和港口巷战。
4. 管理界面：舰队、将领、兵种、装备、任务、关系与设置。

### 5.3 首版战斗原则

- 玩家直接控制水师主帅。
- 士兵由 AI 执行基础移动、索敌、攻击和撤退。
- 玩家通过跟随、坚守、集火、集结和冲锋五类军令影响队伍。
- 首次验证以 20～30 个活跃单位为目标，不追求百人大战。
- 战斗是否成立，以玩家是否需要观察阵型、选择目标和使用军令判断，而不是以单位数量判断。
- 首版舰船战斗采用炮击、接舷和登陆等战斗场景表现，不做真实风帆与航海物理。

### 5.4 现有两幕的定位

- 皇宫场景继续作为序章“奉旨南下”，验证剧情、任务提示和人物关系起点。
- 战船甲板继续作为“初到广州与水师操练”，是混合 2.5D 技术验证的首选背景。
- 技术验证成功后，再决定先迁移甲板还是同时迁移皇宫；默认只迁移甲板，避免一次改动两个剧情场景。
- 当前 64×64 LPC 角色保留作逻辑占位和回归基准，不作为目标战斗美术。

## 6. Steam Demo 内容边界

首个公开 Demo 建议控制在：

- 1 张岭南海疆舆图。
- 1 个主要港口：广州。
- 3 座可访问岛屿。
- 3 张战斗地图：甲板、海滩、岛寨。
- 4 个主要立场：官府、商帮、海民、海盗。
- 5 名可招募或重要剧情英雄。
- 6 个基础兵种。
- 3 类舰船。
- 8～12 个任务。
- 1 名序章海盗首领。
- 约 1.5～2 小时内容。

Demo 明确不包含：

- 多人联机。
- 自由造城。
- 完整风帆、潮汐和舰船驾驶模拟。
- 大规模攻城。
- 随机生成整个世界。
- MOD 编辑器。
- 数十名英雄的复杂关系网。
- 正式版全部港口、岛屿和兵种。

## 7. 美术需求

### 7.1 美术总方向

- 背景：岭南海防题材的 2D 手绘或高精度像素/仿手绘场景，必须使用统一正交投影规范。
- 角色：低模 3D，纯色色块或低饱和贴图，重轮廓、少材质细节，固定镜头下优先保证剪影。
- UI/立绘：2D 手绘，保留当前人物立绘的水墨厚涂方向，但需要统一透明边缘、色温和构图。
- 光照：固定主光方向，角色颜色稳定，不追求写实昼夜变化。
- 阴影：统一脚底软阴影；背景和角色的阴影方向、长度必须一致。
- 比例：锁定镜头后，以角色站立高度、门洞、栏杆和甲板宽度建立一份可复用比例尺。

### 7.2 最小技术验证资产（V0）

这批素材只服务技术判断，不等同于正式美术：

| 类别 | 最小数量 | 要求 |
|---|---:|---|
| 主帅低模 | 1 套 | 标准骨骼、固定披风或简化披风、可识别剪影 |
| 水兵低模 | 1 套 | 模块化头盔/上衣/武器插槽，可生成至少 3 个配色变体 |
| 海盗低模 | 1 套 | 与水兵共享或兼容骨骼，剪影明显不同 |
| 武器 | 4 件 | 刀、长枪、弓/弩、火铳；验证挂点与切换 |
| 动作 | 10 组左右 | 待机、行走、奔跑、两种攻击、受击、死亡、军令、装填、胜利/收势 |
| 甲板背景 | 1 套 | 将现有背景拆成后景、地面、前景遮挡和碰撞参考四层 |
| 材质 | 1 套 | 卡通色阶、轮廓、受击闪白、阵营染色参数 |
| 影子/选中反馈 | 各 1 套 | 脚底软影、友军/敌军选择圈 |
| 特效 | 5 套 | 刀光、命中、箭/弹道、枪烟、死亡/倒地反馈 |

V0 允许使用灰模、商用许可明确的临时动作或程序员材质。判断通过前，不制作皇帝、内侍和全套正式兵种模型。

### 7.3 Steam Demo 角色与单位资产

- 水师主帅：1 套正式模型，2～3 个装备阶段。
- 重要英雄/官员：约 5 套模型或 3 套身体模块加独特头部、服饰和武器。
- 水师单位：刀盾、长枪、弓弩、火铳、炮手、旗鼓兵，共 6 类。
- 海盗单位：近战、远程、火器、精英，共 4 类。
- 海盗首领：1 套独特模型与技能动作。
- 城镇 NPC：4～6 个身体模板，通过服装、头部和配色形成约 12 个外观。
- 舰船：小型哨船、中型战船、旗舰 3 类；海疆舆图使用 2D 舰船图标，本地场景只制作可见甲板部分。

### 7.4 动作资产

共用基础动作：

- 待机、行走、奔跑、转向、受击、倒地/死亡。
- 单手挥砍、长兵器刺击、弓弩射击、火铳瞄准与装填。
- 抱拳、躬身、宣旨、领旨、指挥、擂鼓、举旗。
- 炮手装填、推炮、点火和后坐反应。

动作应优先共享同一基础骨骼。披风、长袍和旗帜可以先采用简化骨骼动画，避免首版引入不稳定的实时布料模拟。

### 7.5 场景资产

Steam Demo 目标：

- 皇宫背景：1 套最终修正版，必要时拆分前景遮挡。
- 广州水师甲板：1 套与锁定镜头匹配的分层背景。
- 海疆舆图：1 张主图，附港口、岛屿、航线、风暴和事件图标。
- 广州港局部场景：1 套。
- 海滩登陆战：1 套。
- 岛寨战场：1 套。
- 海天远景：天空、云层、岛屿剪影、远船、水面共约 10～15 件可复用分层素材。
- 场景道具：火炮、战鼓、兵器架、箱笼、木桶、绳索、旗帜、粮袋、灯笼等约 20～30 件。

### 7.6 立绘、UI 与特效

立绘：

- 主帅、皇帝、内侍、广州县令、重要英雄和海盗首领。
- Demo 约 10～12 名有立绘人物，每人至少 1 张；主角和核心角色提供 2～3 个表情。

UI：

- Logo、主菜单、暂停、设置、存读档。
- 对话框、姓名牌、任务面板、交互提示和教学卡片。
- 海疆舆图、舰队、队伍、兵种、装备、技能与关系界面。
- 普通/悬停/按下/禁用四态按钮。
- 军令、兵种、舰船、资源、关系和任务图标；Demo 预估 60～90 枚。

特效：

- 近战命中、格挡、远程弹道、炮火、枪烟、海浪、水花和尘土。
- 友军/敌军识别、选择、军令范围和目标指示。
- 水墨淡出、军令落印、任务完成与战斗结果反馈。

### 7.7 3D 资产交付规范

- 单位统一使用一套经过确认的基础骨骼；新增骨骼必须说明原因。
- 模型单位按真实尺度导出，约定 1 Godot 单位 = 1 米。
- 面向 Godot 的默认前向遵循项目导入规范，首次验证后固化，不允许每个模型单独修正朝向。
- 角色原点位于脚底中心，武器和特效使用命名统一的 `Marker3D` 挂点。
- V0 建议单个普通士兵约 1,500～3,000 三角面，英雄约 3,000～6,000；最终以性能验证为准。
- 普通单位优先使用 512～1024 像素纹理图集；固定镜头下不制作看不见的高频细节。
- 运行时材质数量尽量控制在每个普通单位 1～2 个。
- 源文件保存 `.blend`，交付 `.glb`；贴图和授权说明与模型一起入库。
- 所有临时、生成、购买和外包素材必须记录来源、许可和可商用范围。

### 7.8 2D 背景交付规范

- 先锁定正交镜头角度、相机尺寸和角色比例，再制作正式背景。
- 每张本地地图至少交付后景/地面、前景遮挡、碰撞参考三类图层。
- 可交互火炮、战鼓、旗帜和箱笼不得全部画死在背景上。
- 运行时避免单张超大 8K 纹理；大地图按构图或区块拆分，单纹理尺寸在目标显卡验证后确定。
- 现有 1344×896 场景可用于 V0；正式 Demo 以 1920×1080 构图验收，并保留更高分辨率源文件。
- 背景阴影方向、角色主光方向和脚底影子必须在美术规范中统一。

## 8. 最小验证计划（MVT）

### 8.1 验证目标

在投入正式角色和地图生产前，回答五个问题：

1. 2D 背景和 3D 角色能否在固定正交镜头下自然贴合？
2. 角色能否正确经过船帆、栏杆、屋檐等前景遮挡区域？
3. 20～30 个带骨骼动画的单位能否稳定运行？
4. 一套骨骼和动作能否无额外手调地复用于水兵、海盗和三种配色变体？
5. “直接控制主帅 + 五种军令”的战斗是否比纯自动互砍更有决策感？

### 8.2 验证场景

在独立实验目录和隔离分支/worktree 中建立“甲板遭遇战”验证场景：

- 使用现有战船甲板作为 V0 背景。
- 1 名主帅、10 名水兵、10 名海盗；性能压力测试提高到 30～40 个单位。
- 一条必须经过前景遮挡的移动路线。
- 一处狭窄通道和一处开阔区域。
- 主帅可移动、普通攻击并使用集结、坚守、集火、冲锋中的至少三项军令。
- 士兵能够索敌、接近、攻击、受击和死亡。
- 显示帧率、单位数、导航耗时和主要错误计数。

该场景不接入正式剧情、世界地图、背包、装备、商店或正式存档。

### 8.3 两周验证步骤

| 时段 | 工作 | 输出 |
|---|---|---|
| 第 1～2 天 | 锁定正交镜头、模型尺度和甲板投影 | 镜头预设、尺度板、三张对比截图 |
| 第 3～4 天 | 导入主帅/水兵灰模、骨骼和基础动作 | 可移动的 3D 角色样例 |
| 第 5 天 | 完成卡通材质、轮廓、脚底影与前景遮挡 | 视觉合成样例 |
| 第 6～7 天 | 建立 3D 碰撞、导航和 10 人跟随编队 | 可重复行走测试 |
| 第 8～9 天 | 加入敌人、攻击、受击、死亡与三项军令 | 最小战斗闭环 |
| 第 10 天 | 增加至 30～40 单位并采集性能 | 性能记录与瓶颈列表 |
| 第 11～12 天 | 修正最高风险问题，不扩功能 | 第二轮验证构建 |
| 第 13 天 | 3～5 名玩家盲测 | 观察记录与问卷结果 |
| 第 14 天 | 评审通过、收缩或回退 | 技术决策记录与下一阶段计划 |

### 8.4 通过标准

视觉：

- 1080p 构图下，角色在五个预设站位的脚底与地面接触误差不超过约 5 像素。
- 指定路线中不存在持续可见的穿帮、脚底漂浮或错误遮挡。
- 主帅、水兵、海盗在缩小到正常游戏尺寸后仍能通过剪影和配色识别。

技术：

- 目标开发机上，1080p、30 个活跃单位的验证场景稳定达到 60 FPS；若最低测试设备不可用，必须记录硬件空缺，不能将开发机结果写成最低配置结论。
- 40 单位压力测试不低于 45 FPS，且无持续增长的内存、节点或导航错误。
- 连续运行 15 分钟无崩溃、单位永久卡死或无法结束战斗的问题。
- 同一动作库能够驱动至少三种单位外观，无需为每个变体单独复制动画。

玩法：

- 至少 4/5 名首次试玩者能在两分钟内理解移动、集结和集火。
- 至少 3/5 名试玩者能描述一次由军令造成的可见战术结果。
- 试玩者不需要开发者口头指导即可开始、结束并重新进行战斗。

### 8.5 失败与回退条件

- 若两轮镜头/背景校准后仍需为每个站位单独修正模型比例，暂停正式背景生产，先重做统一投影模板。
- 若 30 单位在一次基础优化后仍低于 45 FPS，先缩减目标同屏数量至 20，并评估动画 LOD、更新频率和远处替身；禁止直接堆硬件要求掩盖问题。
- 若 3D 角色与背景风格无法融合，先调整模型比例、描边和贴图，而不是同时重画所有背景。
- 若混合 2.5D 合成复杂度超过团队承受范围，回退到“3D 模型离线渲染为 2D 序列帧”的路线 B 变体，继续复用模型和动作资产。
- 若基础军令战斗盲测不能产生可理解的决策，停止扩展世界地图，先重做战斗反馈与单位行为。

## 9. 阶段计划与门禁

| 里程碑 | 目标 | 主要交付物 | 进入下一阶段的门禁 |
|---|---|---|---|
| M0：混合 2.5D 验证 | 证明渲染、遮挡、动画复用与性能 | 甲板验证场景、V0 资产、性能/盲测报告 | 第 8.4 节通过标准达成 |
| M1：战斗原型 | 完成主帅控制、五项军令、基础敌我 AI | 约 15 分钟可重复战斗 | 玩家能理解并使用军令改变结果 |
| M2：数据与海疆原型 | 建立英雄、兵种、舰船、任务、世界状态和存档 | 可航行、进港、战斗、返回的循环 | 存读档后世界状态一致，循环无阻断 |
| M3：序章竖切版 | 接通皇宫、广州、操练、首战和海疆展开 | 45～60 分钟完整流程 | 新玩家无指导可完成，且无进度阻断 |
| M4：Steam Demo | 扩充至 1.5～2 小时并完成美术、音频、设置和 QA | 可公开试玩构建 | 性能、稳定性、输入、分辨率和内容验收通过 |

在单人主导、AI 协作和部分美术外包的假设下，M0 预计两周；从 M1 到 M4 粗略为 4～6 个月量级。该估算只用于安排验证顺序，不是发布日期承诺；M0 结束后必须根据实际资产速度和战斗复杂度重新估算。

## 10. 主要风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 2D 背景与 3D 投影不一致 | 角色漂浮、尺度变化、地图返工 | M0 先锁定相机与比例模板；背景制作必须使用模板 |
| 角色与背景风格割裂 | 画面像两款游戏拼接 | 使用统一色板、轮廓粗细、阴影方向和饱和度基准图 |
| 骨骼动画单位过多 | 帧率下降 | 限制首版单位数、共享材质/动作、降低远处更新频率 |
| 导航与编队互相阻塞 | 士兵挤成一团或卡住 | 编队槽位、分层避让、狭窄区域切换队形 |
| 混合脚本语言增加维护成本 | 测试与重构困难 | 新系统统一 C#，旧 GDScript 只在明确收益时迁移 |
| 二进制资产膨胀 | Git 仓库缓慢、冲突难处理 | 建立源文件/导出文件边界，评估 Git LFS，避免重复导入产物 |
| 参考作品导致范围膨胀 | 长期无法完成 | 首个 Demo 坚持第 6 节边界，不做联机、MOD 和完整海战模拟 |
| 素材许可不清 | 无法商业发布 | 保存来源、作者、许可证和购买凭证，生成素材单独记录 |

## 11. 完成定义

本计划阶段的“完成”不是正式游戏已经制作完成，而是：

- 技术路线、Godot 技术栈、美术交付和最小验证门槛形成一致文档。
- 团队能据此制作 M0，而不需要重新猜测镜头、资产、性能和验收目标。
- M0 未通过前，不批准批量正式美术与大地图内容生产。
- M0 结束后形成明确的继续、收缩或回退决策。

## 12. 下一步决策

在任何实现开始前，需要对以下内容进行一次简短评审并标记批准：

1. 是否确认本地探索/战斗使用 `Node3D + Camera3D`，海疆舆图保留 2D。
2. 是否接受首轮只验证 20～30 个活跃单位，而不是追求百人大战。
3. 是否接受首个 Demo 不做真实舰船驾驶、自由建城、MOD 和多人。
4. 是否接受先使用灰模验证，M0 通过后才制作正式角色。
5. 是否将现有甲板背景作为首个混合 2.5D 验证场景。

评审通过后，为 M0 单独建立 change record、隔离 worktree、测试清单和可提交的分步实施计划。
